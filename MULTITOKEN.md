# Multi-token lending — current design

`pwn_config_poc`, `pwn_hub_poc`, `pwn_proposal_poc`, `pwn_loan_poc` (generated by
`scripts/generate_multitoken.py` + `scripts/multitoken_logic.py`; never edit
`pwn_*/src/main.leo` by hand). Local devnode only; not deployed on any public
network.

## Token families

| Family | Suffix | Required ABI (integration profile v1) |
| --- | --- | --- |
| 1 | `aleo` | `credits.aleo`, u64 |
| 2 | `arc20` | ARC-20 private↔public transfers, `balances: address => u128` |
| 3 | `compliant` | deployed USDCx/USAD signatures, `MerkleProof[2]` with `[field; 16]` siblings, compliance record outputs, `balances: address => u128` |

`Asset = { program_id, token_id (0), family, version (1) }`, part of every
terms/loan hash. A new token with a supported ABI needs one
`pwn_hub_poc::set_asset(token, family, enabled)` transaction, no redeploy. One
program = one family/version forever; `credits` is family 1 only. Delisting
blocks new opens/draws; existing positions still repay, claim, cancel and
withdraw. Not supported: other balance layouts, ARC-21, fee-on-transfer,
rebasing, NFTs. A token issuer's own upgrade can break the fixed ABI.

## Entry points

Proposal: `open_<f>`, `draw_<f>`, `receive_<f>`, `cancel_<f>`, `withdraw_<f>`.
Loan: `accept_<credit>_<collateral>`, `repay_<credit>_<collateral>`, `claim_<collateral>`.
Custody is the program address's public balance; only `pwn_loan_poc` may call
`draw`/`receive`. Native records stay typed, other tokens and compliance records
are `dyn record`; compliance records are returned unchanged before token outputs.
ABI snapshots: `interfaces/`.

## Terms and timing

| Parameter | Bound |
| --- | --- |
| `min_draw`, `max_draw` | u128 atomic units, `0 < min ≤ max` |
| `collateral_ratio`, `repayment_ratio` | bps, `1 … 1,000,000`; repayment ≥ 10,000 |
| `accruing_apr` | bps, ≤ 100,000 |
| `duration` | 10 … 3,153,600 blocks; `expiry` absolute height |
| native credit | `max_repayment + accrued(max_draw, apr, duration × 10 s)` ≤ u64::MAX |

- `collateral = ceil(credit × collateral_ratio / 10⁴)`, `repayment = ceil(credit × repayment_ratio / 10⁴)`.
- Interest accrues **per finalized block** since acceptance:
  `floor(principal × apr × blocks × 10 / 315,360,000,000)`. The borrower can quote
  the exact amount for a target block; real block time sets the effective APR.
  Surplus above the requirement goes to the lender in full.
- `repay_*` needs only an active loan — also after maturity, until the lender's
  `claim_*` (which needs `height ≥ maturity`) finalizes. First finalized wins.
- Repayments accumulate in `repayments[id]` for private `withdraw_*`; they do not
  reopen draw capacity. `cancel_*` withdraws exactly the unused amount and closes
  the commitment; active loans are unaffected.
- Lender/borrower authorization: `BHP256({domain, protocol, account: signer, salt})`.
  Fresh random salt per position; a lost salt strands the position.

## Reserve guard

Before every outgoing transfer and every new `open_*`, the custody program
requires `reserve ≥ liabilities[token]`. After every transfer it requires the
token finalizer changed the reserve by exactly the expected amount; a mismatch
reverts the transaction (the post-transfer reads cause intentional CEI
warnings). Incoming repayments have no precondition, so a deficit in the credit
escrow cannot strand the borrower's collateral. Issuer burn/freeze/pause can
still block payouts in that token; other tokens stay usable.

## Governance

`pwn_config_poc.settings = { admin, upgrader, protocol_fee_bps = 0 }`. Privileged
calls check `std::ctx::caller()` (a multisig program can be admin).
`set_admin` proposes, `accept_admin` by the new admin applies. Upgrades:
`schedule_upgrade(module, edition)` → wait `UPGRADE_DELAY = 720` blocks
(test value) → deploy as `upgrader`; every constructor checks both.
`cancel_upgrade` withdraws a plan. An authorized upgrade can change any
protection; the delay is the users' exit window.

## Validation

```sh
make build          # generate + compile
make unit           # 22 generator/harness/oracle tests
make fuzz           # Leo arithmetic vs unbounded-integer oracle (189 cases)
make test           # 25 credit/collateral pairs, full lifecycle (101 checks)
make invariants     # model-based accounting checks after every action (161)
make security       # adversarial suite (149 checks, 1 real execution proof)
make compatibility  # ABI/storage/constructor/finalizer fingerprints vs reviewed baseline
```

Local devnode with pinned mainnet SOL/WBTC/USDCx/USAD bytecode, public dev keys,
no proofs/certificates/consensus except where stated. Details: [docs/TESTING.md](docs/TESTING.md).

`make security` covers: admission/version/token_id, term bounds on all three
credit families, governance via a hostile intermediary program and two-step
handover, caller restriction on draw/receive, wrong salt / tampered witness /
early claim, repayment after maturity vs. later claim, token substitution
(rejected only at proving time — run with a real proof), delisting and module
pause, default for all nine pairs, invalid compliance proofs, issuer burn on
credit and collateral escrow, pause, freeze-list freeze/unfreeze, amounts above
u64, an inexact test token, unauthorized / too-early / authorized timelocked
upgrade with a live position.

## Deployment notes

Names shorter than 10 characters cost 10^(10 − len) credits: `pwn_hub_poc` 1,000,
`pwn_loan_poc` 100. Program IDs are hardcoded in cross-program authorization;
choose final names before any public deployment. New token semantics → new
versioned profile/entry point; incompatible storage → new deployment. Existing
positions always settle in the programs holding their funds.
