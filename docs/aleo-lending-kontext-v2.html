Proč RFQ nepoužíváme. Půjčka není atomický swap: potřebuje escrow, který přežije transakci, a životní cyklus. Aleo navíc neumí utratit cizí privátní record, takže lender musí kapitál vložit předem tak jako tak. Podepsané nabídky by potřebovaly backend na distribuci, financované commitmenty jsou čitelné přímo z veřejného stavu. Z Arcane zůstala hranice veřejná likvidita / privátní vypořádání a autorizace hashem místo adresy. Z grantového návrhu jsem referenci odstranil.

Příloha A: Detail chatu s ALEO (Discord)

Moje otázka

Hey. Two questions from someone scoping an ANF grant proposal for a lending protocol.

1. Security review. The bug bounty scope looks like it's core protocol only (snarkOS/snarkVM), and the grants page doesn't mention audits either way. For a DeFi program handling user collateral, can a security review be scoped as a grant milestone, or is that expected to be self-funded? If anyone's been through this, I'd love to know what is possible. Also: are there auditors who genuinely know Leo, or is that still a very short list?

2. Lending on Aleo. As far as I explored, nothing related to loans has been deployed to the mainnet yet. Eclipse, AleoIOU, Spectre and Shadowfi all seem to be at various pre-launch or inactive stages, but I'm going off public write-ups rather than chain data, so I may well be wrong. Is that roughly right? And if so, is there a known blocker people keep running into, or is it just that nobody has finished yet?

Odpověď

1. DeFi projects are built by 3rd parties thus their creators should handle their own audits and bug bounty programs. The Foundation is only maintaining the core protocols, which are snarkOS and snarkVM. Grants application can include security review as milestones, however the current grants program is only focusing on established and proven projects partnerships rather than projects built from scratch. There are some audit companies that are experienced in auditing Leo and the Aleo protocols that we can introduce if needed.

2. Yes there's no lending protocol live on Aleo yet. Previous projects are inactive or stopped developing, mostly due to the inability to sustain project maintenance costs and decided not to continue without grants support.

Odpověď (Florent, Eclipse)

Hi Jan,

Thanks for reaching out. Alexandre forwarded your email, I'm replying on behalf of the team. Really glad the work is useful to you. Happy to share whatever we learned.

To your first point, the hardest parts weren't really the code but the infrastructure around Aleo. Nothing really existed to build on. Our first issue was the lack of a usable price oracle, so we ended up building one ourselves before we could even start on the lending side. It worked, but only because we were the ones running it, and being modelled on Chainlink it had no economic sustainability for a team our size.

The second is the one you're probably going to run into: liquidating a position that's private. A liquidator has to be able to prove that someone else's position is unhealthy, and if the numbers sit behind a commitment only the borrower can open, there's no way for them to build that proof. Asking the borrower to prove their own insolvency obviously doesn't work either.

What we did was cut the link between the owner and the data instead of hiding the data. The private record only holds { owner, position_id }, and a public mapping holds the collateral and debt under that anonymous id. Liquidators scan the mapping, spot the unhealthy ids and liquidate, without ever knowing whose position it is. The liquidator then gets paid through a private LiquidatorReceipt record, so consuming it is what proves they're entitled to the collateral, and no address ends up on-chain on either side. What it doesn't do is hide the amounts themselves, which as far as I know nobody has solved on any private chain.

On what we would change: permissionless pools over arbitrary pairs instead of one admin vault, and partial liquidations instead of seizing the full collateral.

As for why it stopped, we were in talks with the Aleo Foundation for funding and it fell through when we were asked to be MiCA compliant for the vault, since it involved issuing a stablecoin. We were confident in the technical direction, it simply wasn't economically viable for us to pursue.
